## 0. 为什么不做物理移动（重要，先说结论）

我尝试了两种物理重组方案，**都失败并已完整回滚**。记录在此以免后人重试：

| 方案 | 做法 | 失败原因 |
|---|---|---|
| **A. 直接移动** | 把 44 个 `A*` 目录移入 `03_实验/`、`05_论文/` 等分组 | 44 个目录共被 **328 处**硬编码引用（`ROOT / "A13_可靠性机制" / ...`）。移动后 **102/177 脚本断链** |
| **B. 移动 + junction 兼容** | 真实目录移入分组，旧路径建 junction | Python 的 `__file__` **始终解析为真实路径**，junction 无法"隐藏"新位置。脚本移入 `05_论文/` 后，`_research_root()` 向上找到的是 `05_论文` 而非研究根 → 仍断链 |

**结论**：本项目的脚本用 `__file__` 定位（124 个文件），物理移动必然破坏相对路径。
**因此采用「导航层」方案：目录不动，但提供清晰的功能索引。**

> 已为此做的**永久性改进**（本轮新增）：
> - `_lib/_find_root.py` —— **标记式**根定位（找 `_PROJECT_ROOT` / `_lib/`，不数层数）
> - `_PROJECT_ROOT` —— 哨兵文件
> - 7 个关键脚本已改用 `_research_root()`；实测**移到 3 层深处仍能自愈**
> - 这使**未来**的小范围移动成为可能（但 328 处硬编码引用仍需先迁移）

## 4. 维护约定

1. **新增分析** → 建 `A<NN>_<主题>/`；编号顺延，**不要**插空号（避免与旧号冲突）。
2. **公共函数** → 放 `_lib/`，用 `_research_root()` 定位，勿用 `parent.parent`。
3. **新脚本定位** → 一律用：
   ```python
   from _find_root import research_root   # 或复制其 _research_root() 实现
   ROOT = research_root()
   ```
4. **改名**：先查 `文件功能清单.md` 的 **REF** 列；REF≥1 者改名必须同步改引用方。
5. **日志** → 由 `_logs/consolidate_logs.py` 自动纳管，勿手工散放。
