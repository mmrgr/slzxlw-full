## 3. ★ 文档卫生门禁的覆盖漏洞

### 3.1 问题
`hygiene_gate.py` 检查"论文引用的产物必须存在"，但它用的正则是：

```python
re.findall(r"`(A\d+_[^`]+\.(?:json|csv|md|bib))`", both)
```

**只匹配这 4 种扩展名。** 于是：

| 类型 | 是否被检查 |
|---|---|
| `.json` / `.csv` / `.md` / `.bib` | ✅ |
| **`.py` 文件引用** | ❌ 漏 |
| **纯目录引用**（如 `` `A29_文献核验/` ``） | ❌ 漏 |

**实际覆盖率：33 个引用中只检查 20 个，漏 13 个（39%）。**

### 3.2 修复
改为匹配所有 `` `A\d+_... ` `` 形式的路径（不限扩展名），并去掉结尾斜杠后验证存在性。

**修复后**：33/33 全部检查，0 缺失。

**再跑突变测试** → 文档卫生门禁**成功杀死**注入的缺陷。

## 4. 一个技术细节：`exit=2` 不是崩溃

突变测试里门禁返回 `exit=2`，我核实了一下：

| 场景 | exit code |
|---|---|
| 正常通过 | 0 |
| 单独运行 + 注入缺陷 | **1** |
| 通过 subprocess 调用 + 注入缺陷 | **2** |

`exit=2` 是 Windows 下 Python `sys.exit(1)` 经 subprocess 的编码差异，**不是脚本崩溃**。

核实方式：检查失败输出中是否有具体的 `[FAIL]` 行。实测：

```
[FAIL] 交叉引用不悬空 (引用 7 个 §N, 悬空 1)
[FAIL] 无非标准编号(bis/ter) (命中 1)
```

**门禁确实定位到了问题，不是崩溃。**

> 这是本项目的又一次"检查逻辑本身需要被检查"——若只看 exit code 而不看输出，
> 会把"崩溃"误当作"通过"，或把"正常失败"误当作"崩溃"。
