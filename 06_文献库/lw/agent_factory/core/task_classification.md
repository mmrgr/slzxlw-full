# 任务分类决策树 — 何时需要多Agent

> **本文件是 System Architect（Phase 2）的核心决策工具。** 在收到需求分析结果后，System Architect 必须按照本文件的决策树，判定任务应该采用哪种架构类型。决策结果写入 `architecture_decision.json`，直接决定后续流程走向。

---

## 一、七种架构类型总览

| 类型 | Agent数量 | 脚本数量 | 并行度 | 典型耗时 | 适用场景 |
|------|----------|----------|--------|----------|----------|
| A. 单Agent足够 | 1 | 0-少量 | 无 | 低 | 简单语义任务 |
| B. 单Agent+脚本 | 1 | 多个 | 无 | 低 | 混合任务，部分可确定性完成 |
| C. 多Agent串行 | 2-5 | 可选 | 无 | 中 | 有明确阶段依赖的流水线 |
| D. 多Agent并行 | 2-8 | 可选 | 高 | 中 | 独立子任务可同时处理 |
| E. 分层多Agent | 3-12 | 可选 | 中-高 | 高 | 复杂任务需分解为子工作流 |
| F. 长期监控型 | 2-6 | 多个 | 中 | 持续 | 需要持续运行/周期执行 |
| G. 人机协作型 | 1-5 | 可选 | 低 | 中-高 | 关键节点需人工确认 |

### 决策流程说明

每个决策节点（Q1-Q5）的判定标准如下：

| 节点 | 问题 | 判定依据 |
|------|------|----------|
| Q1 | 能否用确定性程序完全完成？ | 任务是否只涉及格式转换、数据清洗、校验等无需语义理解的操作 |
| Q2 | 需要语义理解的部分能否由单个Agent完成？ | 语义部分是否足够简单，单Agent上下文是否够用 |
| Q2a | 子任务数量>5且需要分层管理？ | 是否存在"子工作流"概念，是否需要Orchestrator协调多个子流程 |
| Q3 | 子任务间有依赖关系？ | 后续任务是否需要前置任务的输出作为输入 |
| Q3a | 依赖是线性流水线？ | 依赖关系是否构成一条链（A→B→C→D）而非网状 |
| Q4 | 需要人工确认关键节点？ | 是否涉及高风险操作、发布、删除等不可逆行为 |
| Q5 | 需要长期/周期运行？ | 是否需要持续监控、定时执行、事件触发 |

## 三、各类型详细说明与案例

### 类型 A：单Agent足够

**特征**：任务简单，单个Agent的上下文和能力足以覆盖全部需求，无需拆分。

**判定条件**（全部满足）：
- 任务步骤 ≤ 3步
- 不需要多种专业视角
- 输入数据量在单次上下文可处理范围
- 不需要并行加速

**案例**：

```
案例1：把一段中文翻译成英文
  → 单Agent（翻译Agent）
  → 理由：单一任务，无需拆分

案例2：给一篇文章写摘要
  → 单Agent（摘要Agent）
  → 理由：单一任务，输入可控

案例3：检查一段文本的语法错误
  → 单Agent（校对Agent）
  → 理由：单一任务，输出明确
```

**反例**：

```
反面案例：把一段中文翻译成英文，并校对语法，并排版成Word
  → 不应只用1个Agent（翻译+校对+排版是3种不同能力）
  → 应为类型B（单Agent+脚本）：翻译用Agent，校对用Agent，排版用脚本
  → 或类型C（多Agent串行）：如果校对需要独立上下文
```

---

### 类型 B：单Agent + 脚本

**特征**：任务混合了确定性部分和非确定性部分。确定性部分用脚本完成，非确定性部分用单个Agent完成。脚本是主力，Agent做辅助判断。

**判定条件**（全部满足）：
- 任务大部分步骤可确定性完成
- 只有少数步骤需要语义理解
- 不需要多个独立的专业视角

**案例**：

```
案例1：Markdown转Word文档
  → 脚本：pandoc 转换格式
  → Agent：仅在转换失败时解释错误原因
  → 理由：格式转换是确定性的，只有异常解释需要Agent

案例2：批量重命名100个文件（按内容智能命名）
  → 脚本：文件遍历、重命名执行
  → Agent：根据文件内容生成建议文件名
  → 理由：遍历和重命名是确定性的，命名需要语义理解

案例3：从100个JSON文件中提取特定字段并汇总
  → 脚本：JSON解析、字段提取、汇总
  → Agent：仅处理字段名不规范的异常文件
  → 理由：规范文件的提取是确定性的，异常处理需要判断

案例4：扫描代码仓库生成依赖报告
  → 脚本：解析 package.json/requirements.txt 等
  → Agent：分析依赖关系中的潜在风险
  → 理由：依赖提取是确定性的，风险分析需要语义理解
```

**配置示例**：

```json
{
  "architecture_type": "B_single_agent_plus_script",
  "agents": [
    {
      "id": "A1",
      "role": "anomaly_handler",
      "trigger": "script_failure"
    }
  ],
  "scripts": [
    {"id": "S1", "tool": "pandoc", "task": "format_conversion"},
    {"id": "S2", "tool": "python", "task": "file_traversal"}
  ],
  "workflow": "S1 → (失败时) A1"
}
```

### 类型 C：多Agent串行

**特征**：任务有明确的阶段划分，每个阶段的输出是下一阶段的输入，形成线性流水线。各阶段需要不同的专业能力或独立上下文。

**判定条件**（全部满足）：
- 任务可分解为 2-5 个有明确顺序的阶段
- 每个阶段需要不同的专业能力
- 后一阶段依赖前一阶段的完整输出
- 各阶段不能并行（必须等前序完成）

**案例**：

```
案例1：公文写作流水线
  T1: 材料分析Agent → 提取关键信息和要求
  T2: 提纲设计Agent → 根据T1输出设计结构提纲
  T3: 正文撰写Agent → 根据T1+T2输出撰写正文
  T4: 审校Agent → 检查语法、逻辑、格式
  → 理由：每个阶段依赖前一阶段，且需要不同专业能力

案例2：学术论文翻译（保持术语一致性）
  T1: 术语提取Agent → 从原文提取专业术语
  T2: 术语表生成Agent → 建立中英术语对照表
  T3: 翻译Agent → 基于术语表翻译全文
  T4: 一致性校验Agent → 检查术语使用一致性
  → 理由：翻译依赖术语表，校验依赖翻译结果

案例3：竞品分析报告
  T1: 信息收集Agent → 收集竞品公开信息
  T2: 数据分析Agent → 结构化分析收集的信息
  T3: 报告撰写Agent → 撰写分析报告
  T4: 事实核查Agent → 核查报告中的数据准确性
  → 理由：分析依赖收集，报告依赖分析，核查依赖报告
```

**配置示例**：

```json
{
  "architecture_type": "C_multi_agent_serial",
  "agents": ["A1", "A2", "A3", "A4"],
  "workflow_dag": {
    "T1": {"agent": "A1", "depends_on": []},
    "T2": {"agent": "A2", "depends_on": ["T1"]},
    "T3": {"agent": "A3", "depends_on": ["T1", "T2"]},
    "T4": {"agent": "A4", "depends_on": ["T3"]}
  }
}
```

### 类型 D：多Agent并行

**特征**：任务可分解为多个相互独立的子任务，这些子任务可以同时执行，互不依赖。完成后汇总结果。

**判定条件**（全部满足）：
- 子任务间无依赖关系（或依赖可在并行前完成）
- 子任务处理不同的输入数据
- 各子任务的输出可以独立产生
- 并行能显著缩短总耗时

**案例**：

```
案例1：100份独立报告分析
  → 100个报告互相独立，可并行处理
  → 用同一个"报告分析Agent"定义，并行处理100份
  → 最大并发数：4-6（受资源限制）
  → 理由：每份报告独立，无需等待其他报告

案例2：多语言翻译（一篇文章翻译成5种语言）
  → 5种语言翻译互相独立
  → 用同一个"翻译Agent"定义，并行处理5种语言
  → 最大并发数：5
  → 理由：各语言翻译互不依赖

案例3：代码审查（前端/后端/数据库/安全同时审查）
  → 4个审查维度互相独立
  → 4个不同专业视角的Agent并行审查
  → 最大并发数：4
  → 理由：各维度审查可独立进行

案例4：多维度产品评测
  → 评测维度：性能、易用性、安全性、兼容性
  → 4个维度的评测互相独立
  → 并行执行后汇总
  → 理由：各维度评测方法不同但互不依赖
```

**配置示例**：

```json
{
  "architecture_type": "D_multi_agent_parallel",
  "agents": ["A1"],
  "parallel_groups": [
    {
      "group_id": 1,
      "tasks": ["T1", "T2", "T3", ..., "T100"],
      "agent": "A1",
      "max_concurrency": 6,
      "inputs": ["report_001.pdf", "report_002.pdf", "..."],
      "merge_strategy": "collect_to_array"
    }
  ]
}
```

### 类型 E：分层多Agent

**特征**：任务复杂，需要先分解为子工作流，每个子工作流内部再分解为子任务。存在一个Orchestrator协调多个子流程。

**判定条件**（全部满足）：
- 子任务数量 > 5
- 子任务间存在复杂的依赖关系（非纯线性，非纯并行）
- 需要一个协调层管理子工作流的启动和汇总
- 存在"子工作流"概念（一组相关任务形成一个单元）

**案例**：

```
案例1：完整软件项目开发
  Orchestrator
  ├── 子工作流1：需求分析
  │   ├── 需求提取Agent
  │   └── 需求确认Agent
  ├── 子工作流2：架构设计
  │   ├── 技术选型Agent
  │   ├── 架构设计Agent
  │   └── 接口定义Agent（可与架构设计并行）
  ├── 子工作流3：编码实现
  │   ├── 前端开发Agent
  │   ├── 后端开发Agent（可并行）
  │   └── 数据库脚本Agent（可并行）
  └── 子工作流4：测试与部署
      ├── 单元测试Agent
      ├── 集成测试Agent
      └── 部署Agent

  → 理由：4个子工作流，每个内部有并行，子工作流间有依赖

案例2：市场调研报告（含多地区多维度）
  Orchestrator
  ├── 子工作流1：数据收集
  │   ├── 北美市场调研Agent
  │   ├── 欧洲市场调研Agent（并行）
  │   └── 亚太市场调研Agent（并行）
  ├── 子工作流2：数据分析
  │   ├── 定量分析Agent
  │   └── 定性分析Agent（可并行）
  └── 子工作流3：报告生成
      ├── 报告撰写Agent
      └── 校对审核Agent

  → 理由：3个子工作流，数据收集内部可并行

案例3：大规模文档处理流水线
  Orchestrator
  ├── 阶段1：文档分类（并行处理1000个文档）
  ├── 阶段2：按类别处理（不同类别用不同Agent，可并行）
  ├── 阶段3：交叉校验（依赖阶段2全部完成）
  └── 阶段4：汇总报告
```

**配置示例**：

```json
{
  "architecture_type": "E_hierarchical_multi_agent",
  "orchestrator": "O1",
  "sub_workflows": [
    {
      "id": "SW1",
      "name": "data_collection",
      "tasks": ["T1", "T2", "T3"],
      "parallel": true,
      "depends_on": []
    },
    {
      "id": "SW2",
      "name": "analysis",
      "tasks": ["T4", "T5"],
      "parallel": true,
      "depends_on": ["SW1"]
    },
    {
      "id": "SW3",
      "name": "report",
      "tasks": ["T6", "T7"],
      "parallel": false,
      "depends_on": ["SW2"]
    }
  ]
}
```

### 类型 F：长期监控型

**特征**：任务需要持续运行或周期性执行，监控某些状态并在条件触发时执行操作。

**判定条件**（全部满足）：
- 任务不是一次性的，需要长期或周期运行
- 存在"触发条件"概念
- 需要状态持久化以支持跨周期记忆

**案例**：

```
案例1：网站内容变更监控
  监控Agent（周期执行）
  → 检测到变更 → 通知Agent → 人工确认 → 归档Agent
  → 理由：需要周期运行，事件触发

案例2：日志异常检测
  收集脚本（持续运行）
  → 异常检测Agent（周期执行）
  → 告警Agent（触发式）
  → 理由：持续收集，周期分析，触发告警

案例3：竞品价格监控
  爬取脚本（定时执行）
  → 价格分析Agent（每次爬取后）
  → 报告Agent（每周汇总）
  → 理由：周期执行，定期汇总

案例4：学术论文追踪
  检索脚本（每日执行）
  → 相关性判断Agent（对每篇新论文）
  → 摘要翻译Agent（对相关论文）
  → 周报Agent（每周汇总）
  → 理由：周期执行，多阶段处理
```

**配置示例**：

```json
{
  "architecture_type": "F_long_running_monitor",
  "schedule": {
    "type": "cron",
    "expression": "0 */6 * * *"
  },
  "state_persistence": "output/monitor_state.json",
  "agents": [
    {"id": "A1", "role": "detector", "trigger": "schedule"},
    {"id": "A2", "role": "analyzer", "trigger": "A1_output"},
    {"id": "A3", "role": "reporter", "trigger": "weekly"}
  ]
}
```

### 类型 G：人机协作型

**特征**：任务的关键节点需要人工确认或输入，Agent在节点间自动执行，但在检查点暂停等待人工。

**判定条件**（满足任一）：
- 涉及不可逆操作（发布、删除、提交、发送）
- 涉及高风险决策（金额、合同、公开内容）
- 用户明确要求在特定节点确认
- 涉及主观判断（品牌调性、创意方向）

**案例**：

```
案例1：公文正式发布
  T1: 草稿撰写Agent → 生成草稿
  [人工确认点1]：审核草稿内容和方向
  T2: 修改Agent → 根据反馈修改
  [人工确认点2]：最终审核
  T3: 发布脚本 → 正式发布
  → 理由：发布是不可逆操作，必须人工确认

案例2：合同审核
  T1: 条款提取Agent → 提取关键条款
  T2: 风险分析Agent → 分析潜在风险
  [人工确认点]：律师确认风险评估
  T3: 修改建议Agent → 生成修改建议
  → 理由：合同涉及法律风险，需专业人员确认

案例3：营销文案生成
  T1: 创意Agent → 生成3个创意方向
  [人工确认点1]：选择创意方向
  T2: 撰写Agent → 根据选定方向撰写
  [人工确认点2]：审核文案调性
  T3: 优化Agent → 最终润色
  → 理由：创意方向和品牌调性是主观判断

案例4：代码合并到主分支
  T1: 代码审查Agent → 自动审查
  T2: 测试Agent → 运行测试
  [人工确认点]：人工最终确认
  T3: 合并脚本 → 执行合并
  → 理由：主分支合并影响所有开发者
```

**配置示例**：

```json
{
  "architecture_type": "G_human_in_loop",
  "agents": ["A1", "A2", "A3"],
  "checkpoints": [
    {
      "after_task": "T1",
      "type": "approval",
      "prompt": "请审核草稿内容和方向。通过请回复'approve'，修改请回复具体意见。",
      "timeout": "72h",
      "on_timeout": "pause"
    },
    {
      "after_task": "T2",
      "type": "final_approval",
      "prompt": "最终审核。通过后将执行发布。",
      "timeout": "24h",
      "on_timeout": "abort"
    }
  ]
}
```

## 四、经典案例对照表

以下是常见需求的推荐架构类型，供 System Architect 参考：

| 需求描述 | 推荐类型 | Agent数 | 理由 |
|----------|---------|---------|------|
| Markdown转Word | B（单Agent+脚本） | 0-1 | 确定性转换，脚本为主 |
| 单篇文章翻译 | A（单Agent） | 1 | 单一任务 |
| 10篇文章翻译成10种语言 | D（多Agent并行） | 1（复用） | 100个独立任务可并行 |
| 100份报告分析并汇总 | D+E（并行+分层） | 3-4 | 100份并行分析，再汇总 |
| 公文写作（材料→提纲→正文→审校） | C（多Agent串行） | 4 | 线性流水线 |
| 软件项目开发 | E（分层多Agent） | 8-12 | 复杂，需分层管理 |
| 竞品价格监控 | F（长期监控型） | 2-3 | 周期执行 |
| 合同审核与修改 | G（人机协作型） | 3 | 需人工确认风险 |
| JSON格式校验 | B（纯脚本） | 0 | 完全确定性 |
| 论文综述撰写 | C（多Agent串行） | 3 | 提取→综合→核查 |

| 数据清洗+异常解释 | B（单Agent+脚本） | 1 | 清洗用脚本，异常用Agent |

## 五、反过度设计检查清单

在确定架构类型后，System Architect 必须执行以下检查。任何一项不通过，都应考虑降级到更简单的类型。

### 检查项

| 编号 | 检查项 | 不通过时的动作 |
|------|--------|---------------|
| C1 | 每个Agent是否有不可替代的职责？ | 合并职责重叠的Agent |
| C2 | 是否有Agent可以用脚本替代？ | 替换为脚本，降级类型 |
| C3 | 是否有Agent的输出无人消费？ | 删除该Agent |
| C4 | 是否有相邻Agent可以合并而不损失质量？ | 合并 |
| C5 | Agent数量是否与任务复杂度匹配？ | 减少Agent，降级类型 |
| C6 | 是否存在"为了并行而并行"的情况？ | 改为串行 |

### 降级路径

```
E（分层） → D（并行） → C（串行） → B（单Agent+脚本） → A（单Agent）
```

每次降级都应记录理由。如果降级后仍能满足验收标准，则降级是正确的。

### 过度设计的典型信号

| 信号 | 说明 | 示例 |
|------|------|------|
| Agent数量 > 任务步骤数 | 每步一个Agent，但有步骤可以合并 | 5步任务用了7个Agent |
| 存在只做"传递"的Agent | 某Agent只是把上游输出传给下游，无加工 | 删除它，直接连接上下游 |
| 存在只做校验的Agent且校验是确定性的 | JSON校验、数字核对不需要Agent | 替换为脚本 |
| 并行Agent操作同一文件 | 并行写入同一文件会冲突 | 改为串行或拆分输出文件 |
| Orchestrator只管理2个Agent | 分层管理的开销大于收益 | 降级为并行或串行 |

## 七、特殊场景处理

### 场景1：任务规模不确定

当输入规模不确定时（如"分析这些报告"但不知道有多少份），先快速统计输入数量，再决策：

```
输入数量 ≤ 1   → 类型A
输入数量 2-10  → 类型C或D
输入数量 11-50 → 类型D
输入数量 > 50  → 类型D+E（并行+分层汇总）
```

### 场景2：任务混合多种类型

当任务的不同部分适合不同类型时，按主要部分的类型决策，次要部分在内部用脚本处理：

```
案例：100份报告分析 + 生成正式Word报告
  主体类型：D（多Agent并行）处理100份报告
  内部脚本：最后的Word排版用脚本
  → 整体记为类型D，但tool_assignment中标注排版为脚本
```

### 场景3：用户指定了运行模式

| 运行模式 | 架构倾向 | 调整 |
|----------|---------|------|
| 快速模式 | 倾向简单类型 | 能用脚本的不用Agent，能串行的不分层 |
| 标准模式 | 按决策树正常选择 | 无特殊调整 |
| 严格模式 | 倾向完整类型 | 保留审核Agent，增加人机确认点 |
