# 推理脚手架模板 — Reasoning Scaffolds

> **用途**：当 AI Coding Agent 使用 flash 模型或低级模型时，注入以下脚手架模板强制分步推理，补偿思考深度不足。每个脚手架对应一个关键决策阶段。

---

## 使用方式

1. AI Coding Agent 在执行到对应阶段时，读取本文件中对应的脚手架模板
2. 将脚手架模板注入到当前阶段的提示词中
3. 要求 Agent **严格按步骤输出**，每步必须有中间结论
4. 中间结论作为下一步的输入，形成推理链

---

## 脚手架1: 需求分析推理脚手架

**适用阶段**：Phase 1 — Requirement Analyst

**触发条件**：总是触发

```
请按以下步骤分析需求。每步必须输出"中间结论"，不得跳步。

━━━ Step 1: 字面需求提取 ━━━
将用户需求拆解为独立的显性需求点。
- 用户明确说了什么？（逐句提取）
- 用户期望的最终交付物是什么？
- 用户提到了哪些约束条件？
中间结论：[列出所有显性需求点]

━━━ Step 2: 隐含需求推理 ━━━
用户没有说但逻辑上必须包含的需求。
- 要完成交付物，还有什么是必须做的？
- 用户说的约束隐含了哪些其他约束？
- 交付物的使用场景暗示了什么需求？
中间结论：[列出所有隐含需求点]

━━━ Step 3: 输入分析 ━━━
- 输入是什么格式？（文件/文本/URL/数据）
- 输入规模多大？（影响是否需要分块/并行）
- 输入质量如何？（是否需要预处理/清洗）
- 输入是否有敏感信息？
中间结论：[输入特征摘要]

━━━ Step 4: 约束识别 ━━━
- 技术约束：可用的工具、平台、API
- 资源约束：时间、Token、Agent数量
- 质量约束：哪些步骤必须100%准确
- 安全约束：是否涉及隐私/高风险数据
中间结论：[约束清单]

━━━ Step 5: 边缘情况枚举 ━━━
列举至少3个非标准输入或异常场景。
- 如果输入为空怎么办？
- 如果输入格式不标准怎么办？
- 如果输入规模远超预期怎么办？
- 如果某个中间步骤失败怎么办？
中间结论：[边缘情况清单]

━━━ Step 6: 需求优先级排序 ━━━
- P0（必须满足）：[列出]
- P1（最好满足）：[列出]
- P2（可选）：[列出]
中间结论：[优先级排序]

━━━ Step 7: 综合需求陈述 ━━━
基于以上6步分析，用一段话完整描述需求。
- 包含显性和隐含需求
- 包含约束和优先级
- 包含已识别的边缘情况
最终结论：[综合需求陈述]
```

## 脚手架2: 架构决策推理脚手架

**适用阶段**：Phase 2 — System Architect

**触发条件**：总是触发

```
请按以下步骤进行架构决策。每步必须输出"中间结论"。

━━━ Step 1: 任务复杂度评估 ━━━
- 这个任务涉及多少个独立的子任务？
- 子任务之间有依赖关系吗？还是可以独立执行？
- 任务的输入是单一的还是多元的？
- 任务的输出是单一的还是多元的？
中间结论：[复杂度评级：低/中/高 + 理由]

━━━ Step 2: 任务分类 ━━━
按照决策树判断：
- 能用单Agent完成吗？如果能，为什么？
- 能用单Agent+确定性脚本完成吗？
- 需要多Agent串行吗？
- 需要多Agent并行吗？
- 需要分层多Agent吗？
中间结论：[选择的架构类型 + 判断依据]

━━━ Step 3: 方案A设计 ━━━
设计第一个可行方案。
- 需要哪些Agent？各自职责？
- Agent间如何协作？串行还是并行？
- 哪些步骤用确定性程序？
- DAG结构是什么？
方案A：[完整描述]

━━━ Step 4: 方案B设计 ━━━
设计一个与方案A有实质性差异的方案。
- 必须在Agent数量、并行度或分工方式上有本质不同
- 不能是方案A的微调
方案B：[完整描述]

━━━ Step 5: 方案比较 ━━━
在以下维度上比较两个方案：
| 维度 | 方案A | 方案B |
|-----|-------|-------|
| Agent数量 | | |
| 预计Token消耗 | | |
| 并行度 | | |
| 容错性 | | |
| 可维护性 | | |
| 实现复杂度 | | |
中间结论：[比较结果摘要]

━━━ Step 6: 反过度设计检查 ━━━
- 选择的方案是否为了"多Agent"而多Agent？
- 有没有两个职责高度重叠的Agent？
- 有没有可以用确定性代码替代的Agent？
- 有没有可以合并的小任务？
中间结论：[是否通过反过度设计检查 + 修改建议]

━━━ Step 7: 最终决策 ━━━
- 选择哪个方案？
- 理由是什么？（必须引用Step 5的比较结果）
- 有什么风险？（引用Step 6的检查结果）
最终结论：[架构决策]
```

## 脚手架3: 角色设计推理脚手架

**适用阶段**：Phase 4a — Agent Designer（Agent数量>3时触发）

**触发条件**：Agent数量 > 3

```
请按以下步骤设计每个Agent角色。每个Agent都要走一遍这个流程。

━━━ Step 1: 职责定义 ━━━
- 这个Agent要解决什么具体问题？
- 这个Agent的输入是什么？输出是什么？
- 这个Agent的职责能否用一句话描述？
中间结论：[职责陈述]

━━━ Step 2: 职责互斥检查 ━━━
- 这个Agent的职责与其他Agent有重叠吗？
- 如果有重叠，能否合并？还是确实需要分开？
- 这个Agent的职责是否有空白（没有人负责的部分）？
中间结论：[互斥检查结果]

━━━ Step 3: 输入输出设计 ━━━
- 输入需要哪些文件/数据？（只列必要的）
- 输出格式是什么？（JSON Schema）
- 输入是否可以改为引用路径而非复制内容？
中间结论：[I/O定义]

━━━ Step 4: 权限边界 ━━━
- 这个Agent需要读取哪些文件？（read_scope）
- 这个Agent需要写入哪些文件？（write_scope）
- 有没有不必要的权限？
- 有没有可以缩小的权限？
中间结论：[权限定义]

━━━ Step 5: 失败模式分析 ━━━
- 这个Agent可能出什么错？
- 出错后应该怎么处理？（重试/交Reviewer/停止）
- 最大重试几次？
中间结论：[错误处理策略]

━━━ Step 6: 完成条件 ━━━
- 什么情况下这个Agent算完成了？
- 完成的判断标准是确定性的还是需要人工判断？
中间结论：[完成条件]

━━━ Step 7: 禁止行为 ━━━
- 这个Agent不能做什么？
- 有没有安全相关的禁止行为？
中间结论：[禁止行为清单]
```

## 脚手架4: 集成审查推理脚手架

**适用阶段**：Phase 7 — Integration Reviewer

**触发条件**：总是触发

```
请按以下步骤进行集成审查。每步必须输出"中间结论"。

━━━ Step 1: 结构完整性检查 ━━━
- DAG中的所有任务是否都有对应的Agent定义？
- 所有Agent是否都在DAG中出现了？
- 有没有"悬空"的任务（依赖了一个不存在的任务）？
中间结论：[结构完整性评估]

━━━ Step 2: 数据流连贯性检查 ━━━
- 沿着DAG走一遍，每个Agent的输入是否都能从前序Agent的输出获得？
- 数据格式是否匹配？（A的输出Schema = B的输入Schema）
- 有没有"断流"的地方？
中间结论：[数据流评估]

━━━ Step 3: 并行冲突检查 ━━━
- 同一parallel_group中的任务是否写入同一文件？
- 有没有循环依赖？
- 共享资源的访问顺序是否正确？
中间结论：[并行安全性评估]

━━━ Step 4: 异常传播检查 ━━━
- 如果某个Agent失败，下游Agent会怎样？
- 失败是否会被静默吞掉？
- 有没有适当的错误处理和降级策略？
中间结论：[异常处理评估]

━━━ Step 5: 模拟Dry-Run ━━━
在脑海中走一遍完整的执行流程：
- 假设所有Agent都成功，最终输出是什么？
- 假设某个关键Agent失败，系统能否部分交付？
- 假设输入为空或格式错误，系统如何反应？
中间结论：[Dry-Run结果]

━━━ Step 6: 验收标准可验证性检查 ━━━
- 每个验收标准是否都有对应的检查方法？
- 检查方法是确定性的还是需要人工判断？
- 有没有无法验证的验收标准？
中间结论：[验收标准评估]

━━━ Step 7: 全局一致性检查 ━━━
- 所有Agent的指令风格是否一致？
- 配置参数是否冲突？
- 是否有Agent的约束与系统级约束矛盾？
中间结论：[全局一致性评估]

━━━ Step 8: 综合判断 ━━━
- 系统是否可以正常协同工作？
- 有哪些问题需要修复？（按critical/warning/info分级）
- 修复后需要回到哪个阶段？
最终结论：[集成审查结论]
```

## 脚手架5: 通用深化协议

**适用场景**：任何阶段，当检测到浅层思考信号时触发

```
检测到以下浅层思考信号：[列出检测到的信号]

请执行深化推理：

━━━ Round 1: 识别问题 ━━━
- 当前的输出在哪里表现出了浅层思考？
- 具体缺失了什么？（推理步骤/替代方案/边缘情况/验证）
中间结论：[问题定位]

━━━ Round 2: 针对性深化 ━━━
针对缺失的部分重新推理：
- 如果缺失推理步骤：请补充从输入到输出的完整推理链
- 如果缺失替代方案：请提供至少2个替代方案并比较
- 如果缺失边缘情况：请列举至少3个边缘情况及处理方式
- 如果缺失验证：请回答验证清单中的问题
中间结论：[深化后的输出]

━━━ Round 3: 再验证 ━━━
深化后的输出是否通过了验证清单？
- 通过 → 输出
- 未通过 → 标记"需人工审查"，输出当前最佳结果
中间结论：[验证结果]
```

## 脚手架使用建议

| 场景 | 建议使用的脚手架 | Token消耗 |
|------|-----------------|-----------|
| 简单任务（1-2个Agent） | 不使用脚手架 | 0 |
| 中等任务（3-5个Agent） | 脚手架1+2 | 中等 |
| 复杂任务（>5个Agent） | 脚手架1+2+3+4 | 较高 |
| 检测到浅层思考 | 通用深化协议（脚手架5） | 按需 |
| 高风险任务 | 全部脚手架 | 高 |

**Token控制**：脚手架的Token消耗计入深度思考预算（不超过总预算的30%）。如果预算不足，优先保证脚手架1（需求分析）和脚手架2（架构决策）。
