# 深度思考协议 — Deep Thinking Protocol

> **核心目标**：当 AI Coding Agent 使用 flash 模型或低级模型时，通过结构化机制补偿思考深度不足的问题。让"快但浅"的模型也能产出"深且稳"的推理质量。

---

## 一、问题诊断

### flash 模型 / 低级模型的典型缺陷

| 缺陷类型 | 表现 | 后果 |
|----------|------|------|
| **跳步推理** | 直接给结论，省略中间推理链 | 结论不可验证，错误难以定位 |
| **单一方案** | 只给一个方案，不比较替代选项 | 决策质量低，错过更优解 |
| **忽略边缘** | 只考虑主流程，不考虑异常和边界 | 系统在非标准输入下崩溃 |
| **浅层分析** | 表面理解需求，不挖掘隐含约束 | 生成的系统不符合真实需求 |
| **过度自信** | 不质疑自己的结论，不自我验证 | 错误传播到下游 |
| **上下文遗忘** | 处理到后面忘记前面的约束 | 前后矛盾 |
| **模式匹配** | 套用熟悉模式而非分析具体问题 | 方案与问题不匹配 |

### 诊断检测器

在 AI Coding Agent 输出后，执行以下检测（由确定性程序完成，不消耗额外 Token）：

```python
# 伪代码：浅层思考检测器
def detect_shallow_thinking(output, task_type):
    signals = []

    # S1: 输出过短（相对任务复杂度）
    if len(output) < expected_min_length(task_type):
        signals.append("output_too_short")

    # S2: 缺少推理标记词
    reasoning_markers = ["因为", "所以", "由于", "因此", "理由是", "考虑到", "权衡"]
    if not any(marker in output for marker in reasoning_markers):
        signals.append("missing_reasoning_markers")

    # S3: 只有一个方案（决策类任务）
    if task_type in ["architecture", "design"] and output.count("方案") < 2:
        signals.append("single_option_only")

    # S4: 无异常处理考虑
    if "异常" not in output and "失败" not in output and "错误" not in output:
        signals.append("no_error_handling")

    # S5: 无验证步骤
    if "验证" not in output and "检查" not in output and "确认" not in output:
        signals.append("no_verification")

    return signals
```

## 二、补偿机制总览

```
任务输入
    │
    ▼
┌─────────────────────────────────┐
│  机制1: 结构化推理脚手架          │ ← 强制分步推理
│  （详见 reasoning_scaffolds.md）  │
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│  机制2: 多方案强制比较            │ ← 关键决策必须比较
│  至少2个方案 + 权衡分析           │
└────────────────┬────────────────┘
                 │
                 ▼
┌─────────────────────────────────┐
│  机制3: 自我验证清单              │ ← 每个结论必须通过
│  （详见 verification_checklist.md）│
└────────────────┬────────────────┘
                 │
           通过?  │
         ┌───────┴───────┐
         │ 是            │ 否
         ▼               ▼
       输出      ┌────────────────┐
                │  机制4: 迭代深化  │ ← 重新推理（最多2轮）
                │  针对失败项重推   │
                └────────┬────────┘
                         │
                         ▼
                ┌────────────────┐
                │  机制5: 反事实思考 │ ← "如果错了会怎样"
                └────────┬────────┘
                         │
                         ▼
                       输出
```

## 三、机制详解

### 机制1: 结构化推理脚手架

**原理**：flash 模型之所以"浅"，往往不是能力不够，而是没有被迫展开推理。通过强制性的分步模板，把"一步到位"变成"多步到位"。

**使用方式**：在提示词中注入对应的脚手架模板（详见 `reasoning_scaffolds.md`），要求 AI Coding Agent 严格按照模板的步骤输出。

**示例 — 需求分析脚手架**：

```
请按以下步骤分析需求，每步必须输出中间结论：

Step 1 - 字面需求提取
  用户明确说了什么？列出所有显性需求点。
  中间结论：[在此输出]

Step 2 - 隐含需求推理
  用户没有说但逻辑上必须包含的需求是什么？
  中间结论：[在此输出]

Step 3 - 约束识别
  有哪些技术约束、资源约束、时间约束？
  中间结论：[在此输出]

Step 4 - 边缘情况枚举
  列举至少3个非标准输入或异常场景。
  中间结论：[在此输出]

Step 5 - 需求优先级排序
  哪些是必须满足的？哪些是最好有的？
  中间结论：[在此输出]

Step 6 - 综合需求陈述
  基于以上分析，完整描述需求。
  最终结论：[在此输出]
```

**为什么有效**：flash 模型在直接回答"分析需求"时容易给出浅层结果，但在被强制要求"Step 1...Step 6..."时，会逐步展开思考链，每一步的输出都成为下一步的输入，最终质量显著提升。

### 机制2: 多方案强制比较

**原理**：低级模型倾向于给出"第一个想到的方案"。强制要求至少2个方案并进行比较，可以打破这种锚定效应。

**使用方式**：在架构决策、Agent设计等关键阶段，强制要求：

```
请为该任务设计至少2个方案：

方案A：[描述]
  - 优点：...
  - 缺点：...
  - 适用条件：...

方案B：[描述]
  - 优点：...
  - 缺点：...
  - 适用条件：...

比较分析：
  - 在[维度1]上，方案A更优，因为...
  - 在[维度2]上，方案B更优，因为...

最终选择：方案[X]
  理由：[必须是具体的、基于比较的理由，不能是"感觉更好"]
```

**关键约束**：
- 2个方案必须有实质性差异（不是同一方案的微调）
- 比较必须基于具体维度（Token消耗、Agent数量、并行度、容错性、可维护性）
- 选择理由必须引用比较结果，不能凭直觉

### 机制3: 自我验证清单

**原理**：flash 模型不擅长自我纠错，但擅长"回答具体问题"。把"自我检查"变成"回答一组具体问题"，可以显著提高验证质量。

**使用方式**：每个关键输出后，要求 AI Coding Agent 回答验证清单中的问题（详见 `verification_checklist.md`）。

**示例**：

```
在输出架构决策后，请回答以下验证问题：

V1. 这个方案是否满足所有显性需求？逐条对照。
V2. 这个方案是否满足所有隐含需求？
V3. 是否存在更简单的方案可以达到相同效果？
V4. 这个方案在[具体边缘情况]下是否仍然有效？
V5. 这个方案的失败模式是什么？如果失败了会怎样？
V6. 这个方案是否违反了任何核心原则？

如果任何一项回答为"否"或"不确定"，请修正方案。
```

### 机制4: 迭代深化

**原理**：一次推理可能不够深。允许在验证失败后重新推理，但限制最多2轮，避免无限循环。

**使用方式**：

```
迭代1: 初次推理 → 自我验证
  │
  ├─ 全部通过 → 输出
  │
  └─ 有未通过项 → 迭代2

迭代2: 针对未通过项重新推理 → 再次验证
  │
  ├─ 全部通过 → 输出
  │
  └─ 仍有未通过项 → 标记为"需人工审查"，输出当前最佳结果
```

**关键约束**：
- 迭代2只处理未通过项，不重新处理全部内容（Token节约）
- 最多2轮，第3轮直接标记"需人工审查"
- 每轮迭代必须记录"上一轮哪里错了，这一轮如何改进"

### 机制5: 反事实思考

**原理**：低级模型容易过度自信。通过"假设自己的结论是错的"来发现盲点。

**使用方式**：在关键决策后，要求执行反事实思考：

```
假设你刚才的决策是错误的。

Q1: 最可能错在哪里？
Q2: 如果错了，后果是什么？
Q3: 有什么信号可以提前发现错误？
Q4: 基于以上思考，是否需要修改决策？

如果Q4的答案是"是"，请修改并说明修改理由。
```

## 四、触发机制

### 按阶段触发（强制）

以下阶段**必须**启用深度思考协议：

| 阶段 | 触发原因 | 使用哪些机制 |
|------|----------|-------------|
| Phase 1: 需求理解 | 需求理解错误会传播到全流程 | 脚手架 + 验证清单 + 迭代深化 |
| Phase 2: 架构决策 | 架构决策难以中途修改 | 脚手架 + 多方案比较 + 反事实思考 |
| Phase 4a: Agent设计（>3个Agent时） | 角色设计影响协作质量 | 脚手架 + 验证清单 |
| Phase 7: 集成审查 | 需要全局视角 | 脚手架 + 反事实思考 |

### 按复杂度触发

```yaml
complexity_triggers:
  high_complexity:
    condition: "任务涉及 >5 个Agent 或 >3 种输入类型 或 需要联网"
    action: "启用全部5个机制"
  medium_complexity:
    condition: "任务涉及 3-5 个Agent 或 2-3 种输入类型"
    action: "启用机制1+2+3"
  low_complexity:
    condition: "任务涉及 1-2 个Agent 或 单一输入类型"
    action: "启用机制1"
```

### 按风险触发

```yaml
risk_triggers:
  high_risk:
    condition: "涉及法律/医疗/财务结论 或 最终用户可见内容 或 不可逆操作"
    action: "启用全部5个机制 + 迭代深化上限改为3轮"
  medium_risk:
    condition: "涉及总结/分类/分析"
    action: "启用机制1+2+3"
  low_risk:
    condition: "文件重命名/格式转换/机械合并"
    action: "不启用（确定性程序即可）"
```

### 按检测结果触发

当诊断检测器（第一节）检测到浅层思考信号时，自动触发：

```
检测结果: ["missing_reasoning_markers", "single_option_only"]
    │
    ▼
触发动作: 要求重新输出，注入对应的脚手架模板
    │
    ▼
重新检测: 如果仍然不通过，标记"需人工审查"
```

## 五、与 flash 模型的适配策略

### 策略1: 分治降复杂度

flash 模型处理简单问题质量尚可，处理复杂问题容易出错。策略是把复杂问题拆成多个简单问题。

```
复杂问题（flash容易出错）
    │
    ▼ 拆分
简单问题1 → flash处理 → 验证
简单问题2 → flash处理 → 验证
简单问题3 → flash处理 → 验证
    │
    ▼ 合并
综合结论 → 验证
```

### 策略2: 锚定引导

flash 模型容易"跑偏"。通过在提示词中提供锚点（示例、约束、格式要求），减少跑偏概率。

```
锚定示例：
"以下是正确分析的示例格式：
[示例]

请按照相同格式分析以下需求：
[实际需求]"
```

### 策略3: 验证关口

不信任 flash 模型的第一次输出。在每个关键节点设置验证关口，不通过则重试。

```
flash输出 → 验证关口 → 通过 → 继续
                   └→ 不通过 → 重试（带修正提示）
                        └→ 仍不通过 → 标记人工审查
```

### 策略4: 冗余校验

对关键结论，用不同的提问方式问两次，比较答案是否一致。

```
提问1: "这个架构需要几个Agent？为什么？"
提问2: "如果只能用3个Agent完成这个任务，应该怎么分配？如果可以用6个呢？"
比较: 如果两次回答的Agent数量差异大，说明思考不稳定，需要深化。
```

## 六、Token 消耗控制

深度思考协议会增加 Token 消耗。通过以下方式控制：

| 控制手段 | 说明 |
|----------|------|
| **按需触发** | 只在关键阶段和检测到问题时触发，不是所有步骤都触发 |
| **局部深化** | 迭代深化只处理未通过项，不重新处理全部内容 |
| **检测器优先** | 先用零成本检测器检测，有问题再触发深度思考 |
| **预算上限** | 深度思考的Token消耗不超过总预算的30% |
| **缓存中间结论** | 每步的中间结论缓存，重试时不重新推理已通过的部分 |

```yaml
deep_thinking_budget:
  max_token_ratio: 0.30  # 深度思考最多消耗总Token的30%
  max_iterations: 2       # 最多迭代2轮
  max_verification_items: 8 # 验证清单最多8项
  cache_passed_steps: true  # 缓存已通过的步骤
```

## 七、质量度量

每次使用深度思考协议后，记录以下指标（用于评估协议效果并持续改进）：

```json
{
  "deep_thinking_metrics": {
    "triggers": ["phase_1", "phase_2"],
    "mechanisms_used": ["scaffold", "multi_option", "verification"],
    "iterations": 1,
    "verification_passed": 6,
    "verification_failed": 2,
    "verification_fail_items": ["V3", "V5"],
    "tokens_consumed": 3500,
    "modifications_made": true,
    "final_quality_score": 0.85,
    "human_review_required": false
  }
}
```

这些指标会作为评估记忆存入 `memory/evaluation/`，用于优化触发策略。
