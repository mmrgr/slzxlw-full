## 1. 需求分析摘要

**用户原始需求**：构建一个"去AI味系统"，AI Coding Agent扮演6种角色（AI特征检测员/结构重组师/语言人性化师/逻辑深化师/检测模拟员/质量把控师）协作去除文本中的AI生成痕迹。流程为Phase 1检测 → Phase 2三路并行修改 → Phase 3模拟检测 → 迭代（最多3轮）。

**需求分析结论**：
- 任务类型：文本处理系统，输入AI生成文本，输出低AI率文本。
- 核心挑战：AI检测工具（GPTZero/Turnitin/知网等）基于困惑度和突发性两大指标检测AI味，需要系统性消除这些统计特征。
- 关键约束：修改不可破坏原意、数据准确性、引用完整性；不同文体（学术论文/小说/新闻/博客）有不同的"正常"标准和AI率阈值。
- 质量优先级：原意保留 > AI率达标。宁可AI率略高也不可改变核心论点或篡改数据。
- 知识库依赖：需要基于网络研究构建AI味特征知识库、检测规则手册和人性化技术手册（3个知识库文件已由用户预先创建）。

## 2. 架构决策

**决策：多Agent并行修改 + 迭代检测**

理由：
1. **AI味是多维度的**：AI味体现在结构、词汇、统计、逻辑、情感、文体六个维度，单一Agent难以同时精通所有维度的修改。采用多Agent分工，每个Agent专注于1-2个维度的修改，深度更优。
2. **三路并行天然可行**：结构重组（处理structural）、语言人性化（处理lexical+statistical）、逻辑深化（处理logical+emotional）三个Agent处理的特征类别互不重叠，修改同一文本的不同方面，可完全并行执行，max_parallel=3正好覆盖。
3. **迭代闭环必要**：一次性修改无法保证达标。通过"修改→模拟检测→再修改"的闭环，每轮聚焦上轮残留问题，修改密度递减（全面→重点→微调），逐步逼近目标AI率。最多3轮，平衡效果与成本。
4. **质量把控师作为编排者**：合并3路修改结果时可能产生冲突（如结构重组师和语言人性化师同时修改了同一句），需要一位"裁判"解决冲突并确保一致性。质量把控师在Phase 2合并和Phase 3终审两个关键节点出场，是系统质量的最后防线。
5. **检测与修改分离**：AI特征检测员（Phase 1）和检测模拟员（Phase 3）分别负责"找问题"和"验证效果"，不参与修改，避免"既当运动员又当裁判员"的偏见。

**与 Agent Factory 架构原则的对齐**：
- 最小权限：每个Agent的 read_scope/write_scope 精确限定，三个并行修改Agent的 write_scope 为空（不直接写文件，由quality_controller统一合并）。
- 单写者原则：并行Agent写权限不重叠；text_patterns.json 被 ai_detector（Phase 1）和 detection_simulator（Phase 3）写入，但两者不同时执行。
- 确定性优先：3个Schema文件提供机器可校验的数据格式约束。
- 引用路径而非复制内容：Agent通过 read_scope 引用知识库和记忆文件路径，按需加载。

## 3. Agent设计理由

| Agent | 设计理由 |
|-------|----------|
| **ai_detector** AI特征检测员 | 去AI味的第一步是"知道问题在哪"。设独立检测Agent按六大类特征逐项扫描，标注位置和严重程度，为后续修改提供精准靶向。禁止修改原文，确保检测客观性。活跃于Phase 1（每次迭代开头），参考历史AI味模式（text_patterns.json）提高检测准确度。 |
| **structure_reorganizer** 结构重组师 | AI文本的结构模式（三明治/三段式/均匀段落）是最容易被检测工具识别的特征之一（Burstiness低）。设专门Agent处理structural类别，通过案例先行、不对称段落、插入跑题等技术打破结构模式。与语言和逻辑修改互不冲突，可并行。 |
| **language_humanizer** 语言人性化师 | AI高频标记词（此外/综上所述/研究表明）和均匀句式是知网/维普等中文检测工具的重点。设专门Agent处理lexical和statistical类别，通过词汇替换表、句式变化、情感注入、标点个性化来提高困惑度和突发性。 |
| **logic_enhancer** 逻辑深化师 | AI文本的逻辑过于完美平滑（无矛盾、无反例、无不确定性），是腾讯朱雀等深度语义检测工具的识别依据。设专门Agent处理logical和emotional类别，通过引入矛盾、承认不确定、提供反例来打破完美逻辑链。这是"更深层次的人性化"，表面修改不够。 |
| **detection_simulator** 检测模拟员 | 修改后需要验证效果。设独立Agent模拟GPTZero/Turnitin/知网等检测工具，按7个维度评分，估算AI率，标记高风险段落/句子。禁止修改文本和降低标准，确保评分客观。活跃于Phase 3（每次迭代结尾），参考历史模式校准评分。 |
| **quality_controller** 质量把控师 | 3路并行修改需要合并和冲突解决；修改不能破坏原意、数据、引用。设编排者Agent在Phase 2合并3路结果、Phase 3终审，执行10项质量检查清单，更新记忆系统。是系统质量底线守护者，拥有全部4个记忆文件的写权限。 |

**职责互斥设计**：结构重组师不处理词汇/逻辑、语言人性化师不处理结构/逻辑、逻辑深化师不处理结构/词汇、检测员和模拟员不修改文本——从 forbidden_actions 强制隔离。

## 4. 知识库设计（基于网络研究）

本系统的3个知识库文件已由用户预先创建，基于对主流AI检测工具检测原理的网络研究和对大量AI生成文本的特征分析：

| 知识库文件 | 研究来源 | 核心内容 | 使用者 |
|-----------|----------|----------|--------|
| `knowledge/ai_signatures.md` | GPTZero/Turnitin/ZeroGPT/知网AIGC/维普/腾讯朱雀的检测原理研究 | 两大核心指标（困惑度+突发性）+ 六大类AI味特征定义 + 检测清单 + 检测工具矩阵 | ai_detector, detection_simulator |
| `knowledge/detection_rules.md` | 各检测工具的具体检测逻辑和绕过策略研究 | 5种检测工具工作原理详解 + 7维度评分标准 + 各文体检测阈值 + 6条核心原则 + 检测流程模拟 | detection_simulator, ai_detector |
| `knowledge/humanization_techniques.md` | 有效降低AI痕迹的方法汇总和操作示例 | T1-T7七大人性化技术（结构重组/词汇替换/句式变化/逻辑复杂化/情感注入/数据具体化/文体适配）+ 中英文替换表 | structure_reorganizer, language_humanizer, logic_enhancer |

**设计要点**：
1. 知识库引用路径而非复制内容：各Agent通过 read_scope 引用知识库路径，按需加载，避免内容冗余。
2. 知识库可独立更新：检测工具在持续进化，知识库需要定期更新。记忆系统中的 text_patterns.json 记录新发现的AI味模式，可作为知识库更新的候选。
3. 中英文双语支持：知识库同时覆盖中文和英文AI味特征，支持中英文文本处理。

## 5. 深度思考集成

本系统在检测和修改阶段均集成深度思考，参考 Agent Factory 的 `thinking/deep_thinking_protocol.md`：

| 阶段 | 深度思考触发点 | 思考内容 |
|------|---------------|----------|
| **Phase 1 检测** | ai_detector 分析文本时 | 不是简单匹配关键词，而是深入分析每处特征的产生原因、与其他特征的关联、对整体AI率的贡献度。判断哪些特征是"真AI味"需要修改，哪些是文体正常表达不需要修改。 |
| **Phase 2 修改** | 三个修改Agent执行修改时 | 每处修改前思考：修改后是否自然？是否引入新的AI味？是否破坏原意？修改后是否与上下文衔接？使用哪种技术最合适？参考有效策略和失败策略。 |
| **Phase 2 合并** | quality_controller 合并3路结果时 | 深度思考冲突解决方案：当两个Agent修改了同一句时，哪个修改更优？修改后整体是否协调？是否触发过度修改？不可修改内容是否被波及？ |
| **Phase 3 模拟** | detection_simulator 评分时 | 不是简单计数AI高频词，而是模拟检测工具的深层逻辑：逐段估算困惑度和突发性，分析n-gram模式，评估逻辑平滑度，判断标点个性化程度。参考历史模式校准。 |
| **Phase 3 终审** | quality_controller 终审时 | 全局审视：修改后文本是否"像人写的"？是否存在过度修改痕迹？修改对照表是否完整可追溯？记忆系统是否需要更新？ |

**设计理由**：AI味的检测和消除不是简单的模式匹配和替换，而是需要理解文本的深层特征。深度思考协议作为"补偿机制"强制Agent在关键环节进行结构化推理和自我验证，避免浅尝辄止的修改反而引入新的AI味或破坏文本质量。

## 6. 质量保障

1. **不可修改内容清单**：数据/引用/术语/核心论点4类内容严格保护，所有修改Agent的 forbidden_actions 明确禁止修改。
2. **10项质量检查清单**：原意保留、逻辑通顺、语言自然、无过度修改、学术规范、文体一致、AI率达标、无语法错误、无事实错误、修改对照表完整。终审时逐项检查。
3. **过度修改防护**：单轮修改比例不超过原文70%，超出则标记风险。
4. **Schema校验**：3个JSON Schema提供机器可校验的数据格式约束，确保检测报告、模拟报告和修改记录格式一致。
5. **职责互斥**：6个Agent的职责和禁止项明确分离，检测者不改文、修改者不评分、合并者不偏袒。
6. **迭代安全网**：最多3轮迭代，每轮修改密度递减。3轮后仍未达标则输出当前最佳版本+未解决问题清单，不会无限循环。
7. **降级策略**：5级降级应对各种异常情况（文本过长/过短/时间紧迫/文体不明），但原意保留/数据准确性/引用完整性/语言通顺不可降级。

## 7. 已知限制

1. **模拟检测非真实检测**：检测模拟员的评分是基于知识库规则的模拟，与真实AI检测工具（GPTZero/Turnitin/知网）的实际结果可能存在偏差。系统输出的AI率是估算值，不保证100%通过真实检测。
2. **检测工具持续进化**：AI检测工具在不断更新算法，当前知识库中的绕过策略可能随时间失效。需要定期更新知识库和记忆系统中的text_patterns。
3. **过度修改风险**：在追求低AI率时可能过度修改，导致文本不自然或偏离原意。虽然有70%修改比例上限和质量检查清单，但边界判断仍依赖质量把控师的人工裁量。
4. **文体适配局限**：系统支持4种主要文体（学术论文/小说/新闻/博客），但对于诗歌、剧本、法律文书等特殊文体可能需要额外适配。
5. **中文为主**：知识库以中文AI味特征为主，英文支持较为基础。处理纯英文文本时效果可能不如中文。
6. **Token成本**：3轮迭代、每次6个Agent协作、深度思考触发，会消耗较多Token。长文本（>5000字）需分段处理。
7. **格式扩展**：为适配去AI味场景，agent_manifest.json 和 workflow.json 在字段上做了语义化扩展（如 iteration_config、parallel_group、modification_density_by_round 等），与 Agent Factory 原始 JSON Schema 非严格一致，但均为合法JSON。

## 8. 后续优化方向

1. **Agent定义文件补全**：补齐 `agents/` 下 6 个 `{agent_name}.md` 详细执行指导文件，目前 manifest 已定义但详细指导待细化。
2. **真实检测数据校准**：引入真实AI检测工具的检测结果，校准检测模拟员的评分刻度，缩小模拟评分与真实检测的偏差。
3. **记忆Schema化**：为 memory 各文件定义 JSON Schema，支持机器校验记忆记录的完整性。
4. **英文支持增强**：扩充英文AI味特征知识库，提升纯英文文本的处理效果。
5. **更多文体支持**：增加诗歌、剧本、法律文书等特殊文体的处理策略和AI率阈值。
6. **自动化测试**：构建测试用例集（已知AI味的文本+期望检测结果），实现回归测试，确保知识库更新不引入退化。
7. **策略效果统计**：基于记忆系统中的effective/failed_strategies，生成策略效果统计报告，指导知识库优化。
8. **增量修改**：对于多轮迭代，实现增量修改（只重新检测和修改上轮残留问题），减少Token消耗。
9. **Schema对齐**：后续版本可向 Agent Factory 标准 Schema 对齐或扩展 Schema，获得 Factory 工具链的自动校验支持。
